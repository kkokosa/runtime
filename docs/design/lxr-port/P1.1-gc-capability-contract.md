# P1.1 — GC capability negotiation and field-write contract

**Status:** implemented. **Base commit:** `d272dabb7b4857ff388bfb1864eb996dbc9b327c`.

This step adds a generic startup agreement between the execution engine and a garbage collector.
The built-in collector says that it uses the existing card table: a compact table that records which
heap areas may contain new references. A future collector can instead describe one bit of metadata
stored outside the managed heap for each group of field addresses. P1.1 recognizes and checks that
second description, but rejects it because its machine instructions are deliberately the next
roadmap step, P1.2. No LXR collector code is part of P1.1.

## Contract

`GC_INTERFACE_MINOR_VERSION` increases from 8 to 9. `IGCHeap::GetWriteBarrierCapabilities` is
appended after every older virtual method; no existing method moves or changes meaning. It has an
inherited implementation that reports the existing card table. An unchanged collector source
therefore remains a concrete class when rebuilt with the 5.9 header.

The declaration starts with its byte size and structure version. Version 1 has frozen minimum sizes:
40 bytes in a 64-bit process and 32 bytes in a 32-bit process. A call is a bounded exchange:

1. The runtime puts its buffer capacity in `Size` and its highest understood version in `Version`.
2. The collector chooses the highest version both sides understand and writes no more than the input
   capacity.
3. On success, the collector replaces `Size` with the bytes it wrote and `Version` with the version
   it returned.

A version 1 collector therefore answers a version 2 caller with version 1 and 40 or 32 bytes. A
version 2 collector answers a version 1 caller the same way. The inherited implementation writes
each version 1 field separately; it never clears a compiler-sized structure and never writes into a
future caller's tail.

The declaration selects one of these behaviors:

- `CardTable`: the runtime keeps the existing field-write implementation.
- `SideMetadataFieldLog`: before overwriting a managed reference field, the future implementation
  loads an old reference and checks one metadata bit. A set or clear bit, selected by
  `MetadataMeaning`, means that the configured helper must run. The helper receives the field
  address, old reference, and new reference before the field is overwritten and must not start a
  garbage collection.

For field address `D`, the metadata byte is
`MetadataBase + (D >> (GranularityShift + 3))`; the bit in that byte is
`(D >> GranularityShift) & 7`. `MetadataBase` is therefore already adjusted for the collector's
heap address range. This describes LXR's bit that says a field has not yet been recorded,
snapshot-at-the-beginning deletion barriers that record the old reference, and generational field
logs without naming any collector. Reference-count width is not part of this agreement.

The metadata mapping and old-reference order follow the portable LXR-head mechanism at
`304ce69d:src/plan/lxr/barrier.rs:41-83` and
`304ce69d:src/util/metadata/side_metadata/helpers.rs:10-31`. The sequentially consistent transition
and the measured deletion-barrier behavior are checked against the paper-era mechanism at
`df8d30a3:src/plan/barriers.rs:187-319`. These citations describe compiled code in their declared
builds; no `sanity`-only assertion is used as evidence.

## Startup and compatibility

The runtime first requires the collector's major interface version to equal 5. Both lower and higher
major versions are rejected before `GC_Initialize`, because their virtual-method layout may differ.
Only major version 5 with minor version 9 or later can use the appended method.

The runtime checks the declaration after `GC_Initialize` returns but before publishing
`g_pGCHeap`. Invalid size, version, kind, addresses, shift, bit meaning, helper, or reserved bytes
return an error. A valid side-metadata request returns `E_NOTIMPL` with a direct diagnostic in P1.1.
It never falls back to the card table and never leaves a partially published heap.

| collector and runtime | behavior |
|---|---|
| 5.8 collector, 5.9 runtime | The runtime does not call the appended virtual method and selects the existing card table. |
| 5.9 collector, 5.8 runtime | The older runtime ignores the appended method and keeps its existing card table. |
| unchanged collector source rebuilt with the 5.9 header | It inherits a valid card-table answer, builds without adding a method, and runs through the real standalone loader. |
| 5.9 collector, 5.9 runtime | The runtime calls and validates the declaration once before heap publication. |
| collector with major version below or above 5 | CoreCLR and NativeAOT reject it before initialization. |

Selection occurs once in `InitJITWriteBarrierHelpers`. The `CardTable` arm calls the same
`WriteBarrierManager::Initialize` function as before. Managed field writes have no new family test,
load, jump, or instruction.

## Architecture and precompiled-code accounting

| surface | evidence |
|---|---|
| Windows x64 CoreCLR | Built and executed in Workstation and Server modes. |
| Windows x86 CoreCLR | Cross-built; not executed on the x64 host. |
| Windows ARM64 CoreCLR | Cross-built; not executed on the x64 host. |
| ARM32, LoongArch64, RISC-V64 | Their existing barrier assembly and patchers are unchanged. The common declaration and validation were source-audited, but these targets were not cross-built or executed here. |
| WebAssembly | Its static barrier remains unchanged. The target was source-audited, not built or executed here. |
| ReadyToRun | `READYTORUN_HELPER_WriteBarrier` still maps to `CORINFO_HELP_ASSIGN_REF`. ReadyToRun-on and ReadyToRun-off captures were identical. |
| NativeAOT | It performs the same startup validation and explicit rejection. Its x64 `Rhp*` barrier object is instruction-identical; NativeAOT execution was not run. |

P1.1 does not claim to implement side-metadata writes on any architecture. P1.2 owns x64 machine
instructions, and P1.3 owns bulk copies, interlocked writes, and every remaining reference-store
path.

### Regression measurement

The repaired P0.5 harness ran the declared four-scenario subset at heap factor 1.3 for Workstation
and Server GC: 3 invocations per cell, 3-second warmup, and 60-second measurement. All 24 invocations
were valid and the harness's 58 unit checks passed. This run is a health check, not a precise
before/after comparison: the committed P0.5 numbers came from a different session and the machine
has shifted substantially since then.

A paired 10-run smoke comparison measured Workstation at 180.10 ms baseline and 179.50 ms changed
(-0.33%), and Server at 193.73 ms baseline and 192.36 ms changed (-0.71%). Both differences are
inside the approximately ±1.35% uncertainty previously established for 60-second runs on this
machine. They do not prove a speedup. The byte-identical generated instructions are the primary
proof that the built-in field-write path has no added cost.

A final post-review repetition was unusably noisy: individual Workstation runs ranged from about
298 ms to 2,708 ms, and Server runs ranged from about 268 ms to 4,477 ms. Its arithmetic means
showed -21.03% and -44.34%, but those numbers are machine interference, not believable changes from
startup-only negotiation. No performance conclusion is drawn from that repetition.

## Remaining limitations

- The side-metadata implementation is intentionally absent until P1.2 and P1.3.
- Only x64 was executed. x86 and ARM64 were compilation-only; ARM32, LoongArch64, RISC-V64, and
  WebAssembly were source-audited only.
- NativeAOT startup validation and x64 barrier bytes were built, but no NativeAOT application ran.
- `P0.6-measurement-repair.md` is not present on this branch. The known ±1.35% uncertainty supplied
  by the prior work is therefore reported, not re-derived from an absent artifact.
